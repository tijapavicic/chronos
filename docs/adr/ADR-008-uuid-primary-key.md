# ADR-008 – Use UUID as Primary Key for Entities

| Property    | Value                        |
|-------------|------------------------------|
| **Status**  | Accepted                     |
| **Date**    | 2025-01-01                   |
| **Authors** | Chronos Team                 |

---

## Context

The `Facility` entity (and future domain entities) require a primary key strategy.
The two common options in JPA are auto-incremented numeric sequences and UUIDs.

Chronos is envisioned as a component within a larger distributed simulation platform
(SE Platform – see `se-flow-lvl-3.mmd`), where entities may eventually be exchanged
between services (SE Backend, SaS Repository, Calc Service).
In such a context, globally unique identifiers are preferable to avoid ID collisions across
databases and simplify event payloads.

## Decision

Use **`java.util.UUID`** as the primary key type for JPA entities, generated by the JPA provider
(Hibernate) using `@GeneratedValue(strategy = GenerationType.UUID)`.

```java
@Id
@GeneratedValue(strategy = GenerationType.UUID)
private UUID facilityId;
```

`GenerationType.UUID` was introduced in JPA 3.1 (Hibernate 6.x / Spring Boot 3.x) and delegates
UUID generation to Hibernate, which uses a time-based v7 UUID by default for good index locality.

## Alternatives Considered

| Alternative                          | Reason Rejected                                                          |
|--------------------------------------|--------------------------------------------------------------------------|
| `GenerationType.IDENTITY` (auto-int) | Sequential integers collide across distributed databases; hard to merge data sets |
| `GenerationType.SEQUENCE`            | Database-specific sequences; same collision risk across services         |
| Application-managed UUID (`UUID.randomUUID()` in constructor) | Works but bypasses Hibernate's optimised UUID strategy |
| ULID / TSID                          | More sortable but requires a third-party library; UUID v7 (via Hibernate 6.x) is sufficient |

## Consequences

**Positive**
- IDs are globally unique across services and databases with no coordination required.
- Entities can be created offline (client-side) and later persisted without ID conflicts.
- Simplifies event-driven architectures where entity references cross service boundaries.

**Negative / Trade-offs**
- UUIDs (16 bytes) consume more index space than 4- or 8-byte integers, leading to slightly larger B-tree indexes.
- UUID values are non-sequential by default (UUID v4), which can cause page fragmentation in B-tree indexes; Hibernate 6.x mitigates this with time-ordered UUID v7.
- UUID values are harder to read and type manually during debugging compared to small integers.
